# Task Planner

## 사용 시점
새로운 시험 과제, 코드베이스, 요구사항이 주어져 필수 조건과 작업 순서를 빠르게 정리해야 할 때 사용한다. 간단한 작업에는 짧은 계획만 제시한다.

## 절차
1. **읽기**: 실제 과제의 `README.md`, 입력 데이터 설명, 제출 안내와 현재 파일 목록을 확인한다. 존재하지 않는 문서는 요구하지 않는다.
2. **추출**: 목표, 필수 기능, 입력과 출력, 형식과 경로, 제약, 평가 방법, 금지 사항을 구분한다.
3. **분류**: `필수 / 있으면 좋음 / 미확인`으로 나눈다. 문제에 없는 요구사항을 추가하지 않는다.
4. **계획**: 3~5개의 작은 단계에 각 1개 이상의 확인 가능한 완료 조건을 지정한다. 처음 단계는 최소 실행 가능한 결과물을 우선한다.
5. **실행**: 사용자가 구현까지 요청했으면 필요한 자료가 확보되는 즉시 코딩으로 넘어간다. 승인만을 기다리며 멈추지 않는다.
6. **진행 기록 시작 (기본 동작)**: 프로젝트 루트의 `PROGRESS.md`를 **반드시 확인하고 갱신한다**. 이미 있으면 기존 기록을 유지하고, 없으면 간단한 기록 파일을 생성한다. 설치된 템플릿이 있으면 활용한다. 현재 단계, 3~5개 계획의 완료 조건, 아직 미확인인 항목과 다음 행동을 기록한다. 단, 공식 과제가 기록 파일 작성을 명시적으로 금지하거나 쓰기가 불가능한 경우에는 파일을 만들거나 갱신하지 않고 대화 메모로 대체한다.
7. **단계 완료 추적**: 주요 단계가 끝날 때마다 실제 변경 파일, 실행한 검증 결과, 미해결 문제와 다음 행동을 `PROGRESS.md`에 **반드시 짧게 갱신한다**. 명령어마다 반복 기록하거나 별도 JSON 및 여러 상태 파일을 만들지 않는다. 공식 과제의 명시적 기록 금지 또는 쓰기 불가 예외에서는 대화 메모만 사용한다.

## 출력
- 필수 요구사항 (최대 8개)
- 미확인 정보 / 해결 방법
- 단계별 작업과 완료 조건 (간결한 표 또는 목록)
- 첫 번째 실행 행동
- `PROGRESS.md` 생성/갱신 결과 (기본적으로 수행하며, 공식 금지 또는 쓰기 불가 시 그 사유 보고)

## 경계
- 실제 코드 구현에 없는 성능 수치, 테스트 결과나 기능을 계획서에 완료된 것처럼 쓰지 않는다.
- 프레임워크와 명령어는 프로젝트 내용을 확인한 후 결정한다.
- 공식 지침과 충돌하는 요청은 해당 부분을 수행하지 않는다.
