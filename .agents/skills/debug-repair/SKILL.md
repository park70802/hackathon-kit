# Debug Repair

## 사용 시점
실제로 발생한 빌드 실패, 예외, 테스트 실패, 데이터 처리 문제, 브라우저 동작 오류가 있을 때 사용한다.

## 절차
1. 오류를 재현하거나 제공된 정확한 로그를 읽는다. 오류 메시지와 발생 경로를 보존한다.
2. 실패 지점, 예상 동작, 실제 동작을 한두 문장으로 정리한다.
3. 관련 파일만 확인하고 가능한 원인을 1~3개로 좁힌다. 웹 UI 과제라면 `WEB_SPEC.md`가 있는지 확인해 기대하는 화면 구조와 사용자 흐름을 참조한다. 공식 README와 실제 동작이 이 문서보다 우선한다.
4. 가장 위험이 낮은 원인부터 **작은 수정**을 적용한다. 관련 없는 파일과 동작하는 기능을 재작성하지 않는다.
5. 같은 명령 또는 같은 입력으로 다시 검증하고 회귀 여부를 확인한다.
6. 두 차례 유사한 수정으로 해결되지 않으면 새로운 증거를 수집해 가정을 수정한다. 무작정 반복하지 않는다.
   - 웹 UI의 페이지 구성, 주요 컴포넌트 또는 사용자 흐름을 실제로 변경했다면 `WEB_SPEC.md`도 변경된 설계에 맞게 갱신한다. 단순 버그 수정 이력과 검증 로그는 `PROGRESS.md`에만 남긴다. 웹 UI가 아니거나 `WEB_SPEC.md`가 없다면 억지로 생성하지 않는다.
7. 오류를 처리한 뒤 프로젝트 루트의 `PROGRESS.md`를 **반드시 갱신한다**. 파일이 없으면 생성한다. 오류 증상, 원인과 근거, 변경 파일, 동일 조건 재검증 결과, 남은 문제를 간결하게 기록한다. 실패 또는 미확인도 그대로 기록하고 이전 기록을 삭제하지 않는다. 단, 공식 과제가 기록 파일 작성을 명시적으로 금지하거나 쓰기가 불가능하면 파일 대신 대화에 보고한다.

## 결과 보고
- 원인: 로그 또는 실행 근거 포함
- 수정: 파일과 변경 요약
- 검증: 명령 및 통과/실패/미실행 상태
- 남은 위험: 있으면 명시

## 경계
- 테스트 실패를 숨기려고 검증 조건을 삭제하거나 약화하지 않는다.
- 외부 네트워크, 권한, 환경 격리, 감독 제한을 우회해서 오류를 해결하지 않는다.
- 테스트를 실행하지 않았다면 성공했다고 주장하지 않는다.
